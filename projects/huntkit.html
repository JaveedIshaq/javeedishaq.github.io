01 / The problem

Tailoring a resume for every job is slow — and AI tools make things up.

Job seekers paste a description into a chatbot and get confident bullets about projects they never did. I wanted the opposite: answers you can trust because each one points back to a specific part of your own profile.

02 / Architecture

Two pipelines: ingest once, retrieve per job.

03 / Key decisions

Trade-offs I made on purpose.

pgvector inside Postgres, not a separate vector DB

One database for users, jobs and embeddings keeps joins simple, backups in one place and hosting cheap for an MVP.

Every chunk goes to the model with its id

Retrieved chunks are labelled with their chunk id and source, strengths come back referencing those ids, and the API returns the citations to the dashboard.

No evidence, no model call

If retrieval finds no profile context, the API records a low_context run and asks the user to add sources instead of letting the model guess.

AI-run observability from day one

Every analysis logs model, token counts, latency, status and the retrieved chunk ids to an ai_runs table, so bad answers can be debugged instead of guessed at.

// profile-retrieval.service.ts
const results = await this.prisma.$queryRaw<RetrievedChunk[]>`
  SELECT c.id, c.content, ps.title AS source_title,
         1 - (c.embedding <=> ${vectorLiteral}::vector) AS score
  FROM profile_chunks c
  JOIN profile_sources ps ON ps.id = c.profile_source_id
  WHERE c.user_id = ${userId}::uuid AND ps.status = 'ready'
  ORDER BY c.embedding <=> ${vectorLiteral}::vector
  LIMIT ${limit}
`;
